# E2E 测试概念与自动化框架选型

> 适用范围：帮助理解 E2E（End-to-End，端到端）测试在测试体系中的定位、可选的自动化框架，以及本项目接入自动化 E2E 的建议路径。
> 有效状态：长期有效的技术笔记；框架格局会随时间变化，选型结论以实际验证为准。
> 姊妹篇：《Web服务端到端测试方法.md》记录手工/半自动 E2E 的具体操作手册，本文解释"为什么、用什么框架自动化"。

## 一、E2E 在测试体系中的位置

| 层级         | 测什么               | 例子（以 Web 服务传书为例）                                                             |
| ------------ | -------------------- | --------------------------------------------------------------------------------------- |
| 单元测试     | 单个函数/类的逻辑    | 给 `addLocalBook` 传构造好的参数，断言返回值                                            |
| 集成测试     | 几个模块拼起来的接口 | LocalBook + 数据库 + 文件写入连起来测                                                   |
| **E2E 测试** | **真实用户全链路**   | 浏览器上传文件 → 请求进设备里的服务器 → 文件落盘 → 书入数据库 → 书架显示 → App 弹 Toast |

**E2E 的独特价值：专抓层与层之间"接缝"上的 bug。** 2026-09 修复的传书失效问题是现成案例：编译通过、单测可过、代码审读也未发现，因为根因（serve() 重写 content-type 时剥掉 multipart boundary）藏在 HTTP 头处理的接缝上——单元测试构造的参数绕过了 HTTP 层，永远触发不了。直到用 curl 发了一个真实 multipart 请求，服务端当场回 "boundary missing"，根因才暴露。任何横跨「客户端 ↔ 服务端 ↔ 存储/系统」的功能改动，都值得跑一遍 E2E。

## 二、为什么需要自动化框架

手工 E2E（或 AI 驱动的半自动 E2E，如用 browser-use + android-emulator 现场操作）的问题：

- **不可重复**：每次改动后都要人或 AI 照文档重新走一遍；
- **不进 CI**：GitHub Actions 推送后自动跑的检查里没有它，回归全靠自觉；
- **无断言沉淀**：验证结论存在于对话里，而不是一条可执行的脚本。

自动化框架把这些步骤写成脚本：一条命令重复执行、失败自动报警、可挂进 CI 每次提交都跑。

## 三、Android 端框架

| 框架                            | 类型               | 特点                                                                                                                    | 适合场景                                          |
| ------------------------------- | ------------------ | ----------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| **Espresso**（Google 官方）     | 白盒、instrumented | 测试代码打进 APK 随应用跑，按控件 id 精确定位，速度快结果稳；与 Compose 测试同生态（`createComposeRule`）               | 应用内页面流程回归（如"打开设置→改端口→保存"）    |
| **UI Automator**（Google 官方） | 黑盒、跨应用       | 能操作系统弹窗、SAF 文件选择器、通知栏、桌面                                                                            | 与 Espresso 配合处理系统对话框步骤                |
| **Maestro**                     | 黑盒               | YAML 写流程、安装简单、自带容错（自动等元素）、`maestro test 流程.yaml` 即可在真机/模拟器执行；复杂断言能力弱于代码框架 | 快速上手的黑盒关键链路回归，最贴近手工 E2E 的形态 |
| **Appium**                      | 黑盒、跨平台       | WebDriver 协议，Android/iOS 共用脚本；环境重、速度慢、脚本易碎                                                          | 有专门测试团队、需双端共用脚本的场景              |
| Detox                           | 灰盒               | 绑定 React Native 生态                                                                                                  | 本项目不适用                                      |

## 四、Web 端框架

- **Playwright**（微软出品）：当前主流。TypeScript 写脚本，原生支持下载监听、自动等待、无头浏览器、trace 调试。《Web服务端到端测试方法.md》里 browser-use 用的就是 Playwright 风格 API，动作几乎可原样翻译成 Playwright 脚本。
- Selenium：老牌，生态广但比 Playwright 笨重；Cypress：同类竞品，多标签页与下载处理偏弱。新项目一般首选 Playwright。

## 五、本项目接入建议（三层，克制覆盖）

1. **网页层（性价比最高，建议第一步）**：Playwright 脚本 + `adb forward`。例如备份链路：打开备份页 → 点「点击下载备份压缩包」→ 断言下载事件与「备份成功」面板。不依赖任何 App 端框架，设备开着 Web 服务就能跑；CI 中先起 Android 模拟器装 APK 再转发端口即可。
2. **App 层**：Maestro 写传书/备份两条关键链路的 YAML（开 Web 服务 → curl 传书 → UI 树验证书架），黑盒方式与手工验证一致，上手成本最低。需要精细控件操作时再引入 Espresso（`androidTest/`）。
3. **范围克制**：E2E 慢且对环境抖动敏感，只覆盖传书、备份等核心链路，不要追求全覆盖；界面细节交给单元测试与人工 review。

## 六、术语表

| 术语              | 含义                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------- |
| 白盒              | 测试代码能访问应用内部（控件 id、类名、状态）                                           |
| 黑盒              | 只像普通用户一样操作界面                                                                |
| instrumented 测试 | 随 APK 一起装进设备、在设备上运行的测试（Espresso 属于此类，放 `androidTest/`）         |
| 无头浏览器        | 不打开窗口、专为自动化运行的浏览器（Playwright 默认模式）                               |
| CI                | Continuous Integration，持续集成；GitHub Actions 即此类服务，推送代码后自动跑构建与检查 |
| 断言              | 脚本里的"预期检查"，不满足即判定测试失败                                                |
