# 代码耦合度 / 屎山程度扫描分析

> 定位：一次性的架构诊断分析，结论供后续重构决策参考。
> 状态：**分析中，尚未开始改造**。落地完成后本文件应归档处理（见 CLAUDE.md 收尾规则）。
> 适用范围：`io.legado.app` 源码，基于当前 master 快照。

## 结论速览

按「耦合度 × 改动难度 × 症状严重度」评估，屎山最严重的前三处：

| 排名 | 位置 | 规模 | 核心问题 |
| --- | --- | --- | --- |
| 🥇 1 | `model/ReadBook.kt` | 50KB / 1375 行 | 全局 god object，中心辐射式依赖枢纽，数据实体逆向依赖 |
| 🥈 2 | `help/JsExtensions.kt` | 41KB | Rhino JS 桥接「能力全集」接口，契约禁区，无人敢改 |
| 🥉 3 | `model/AudioPlay.kt` + `VideoPlay.kt` + `ReadManga.kt` | 16~26KB ×3 | 同一套全局单例 anti-pattern 复制三份 |

## 🥇 No.1：`model/ReadBook.kt` — 全局 god object，中心辐射式依赖枢纽

**定义（病根所在）：**

```kotlin
@Suppress("MemberVisibilityCanBePrivate")
object ReadBook : CoroutineScope by MainScope() {
    var book: Book? = null
    var callBack: CallBack? = null
    var inBookshelf = false
    ...
}
```

### 三个致命点

1. **全局 `object` + 自造协程作用域**
   一个没有任何生命周期管理的常驻单例，直接 `: CoroutineScope by MainScope()`。这违反了项目的 Scope 规范（ViewModel 用 `viewModelScope`、生命周期感知场景用 `repeatOnLifecycle`）。它只有进程死亡才回收，协程泄漏风险敞口巨大。

2. **一个类管至少五件不该它管的事（职责违反）**
   - 阅读进度状态：`durChapterIndex` / `durChapterPos` / `setProgress`
   - 章节加载：`chapterLoadingJobs` + 三个 Mutex（prev/cur/next）
   - WebDAV 进度同步：`uploadProgress` / `syncProgress`
   - 离线缓存下载协调：`downloadedChapters` / `downloadFailChapters` / `preDownloadSemaphore`
   - 阅时统计：`ReadSessionRecorder`

3. **引用面 47 处 / 20 个文件，横跨四层**
   已经不止是「耦合」，而是**层层逆依赖**：
   - `api/controller/BookController.kt`（网络接口层）
   - `base/BaseActivity.kt`（基类）
   - `data/entities/Book.kt`（**数据实体反向依赖全局状态**——`Book.delete()` 里直接 `ReadBook.book = null`）
   - `service/BaseReadAloudService.kt` / `ExportBookService.kt` / `HttpReadAloudService.kt` / `TTSReadAloudService.kt`
   - `receiver/MediaButtonReceiver.kt`
   - `ui/book/read/` 下大量 View 与 Dialog

### 为什么最难改

没有接口、没有依赖注入（Hilt 管不到 object 的静态字段）。要拆必须：

1. 先提纯出 `ReadingSession`（进度状态）、`ProgressSync`（WebDAV 同步）、`DownloadCoordinator`（离线缓存）三个带接口的组件；
2. 再把 20 个调用点逐个迁移；
3. 最后剥掉 `Book.kt` 对 `ReadBook` 的逆向依赖。

任何字段挪窝，`BaseReadAloudService` / `MediaButtonReceiver` / `Book.kt` 全得跟着动。保守估计是**按周计**的活。

## 🥈 No.2：`help/JsExtensions.kt` — Rhino JS 桥接「能力全集」接口

**定义（病根所在）：**

```kotlin
@Keep
@Suppress("unused")
interface JsExtensions : JsEncodeUtils {
    fun ajax(url: Any): String? { ... }
    fun webView(html: String?, url: String?, js: String?): String? { ... }
    fun openVideoPlayer(url: String, title: String) { ... }
    fun startBrowser(url: String, title: String) { ... }
    ...
}
```

一个 **interface** 里堆了 41KB 的默认实现，是书源规则引擎的能力全集：

- 网络：`ajax` / `ajaxAll` / `ajaxTestAll` / `connect`
- WebView 抓取：`webView` / `webViewGetSource` / `webViewGetOverrideUrl`
- 播放器：`openVideoPlayer`
- 浏览器：`startBrowser`
- 以及 sourceVerification / 文本处理 / 正则 / 字符集转换 / 自定义规则……

### 为什么最难改

接口是最难变更的耦合点。任何实现它的类（`SourceRuntime`、`SourceVerification` 等）都会因为增删一个成员而强制同步。它是**所有书源脚本的契约**，改它 = 动所有书源脚本的兼容性，是生死线，没人敢碰。

## 🥉 No.3：`model/AudioPlay.kt` + `VideoPlay.kt` + `ReadManga.kt` — 同一套 anti-pattern 复制三份

三个 16~26KB 的 `object`，和 `ReadBook` 一个模子刻出来的：

- 全局可变状态：`var book: Book?`、`var bookSource`
- 全局 scope
- 直接读写数据库
- `AudioPlay` 被 `SourceHelp.getSource` 一起兜底查询

**同一套 anti-pattern 复制了三份**，修好一个也得再修俩。

---

## 一句话总评

- `ReadBook` 是**责任的泥潭 + 依赖的中心**。
- `JsExtensions` 是**契约的禁区**。
- `AudioPlay / VideoPlay / ReadManga` 是**anti-pattern 的复制粘贴**。

要动架构，先把 `ReadBook` 按职责劈成 `ReadingSession / ProgressSync / DownloadCoordinator` 三个带接口的组件，再把 `Book.kt` 对 `ReadBook` 的逆向依赖剥掉——不然连加个字段都怕炸。

---

## 后续建议

- 重构优先级：`ReadBook` 拆分 > 剥除 `Book.kt` 逆向依赖 > `AudioPlay/VideoPlay/ReadManga` 统一改造。
- `JsExtensions` 拆成按能力域的多个接口（网络 / WebView / 播放器 / 工具），通过组合而非继承暴露给 Rhino，但需评估对存量书源脚本的兼容影响。
- 拆分后所有新组件必须走 Hilt 注入 + 生命周期感知 scope，杜绝新的全局 `object` 协程作用域。
